Pipeline CI/CD do back-end

O caminho de uma história do Jira desde a feature branch até produção. Cada etapa diz o que roda, quem bloqueia o merge e qual prática do Martin Fowler ou requisito do projeto (RNF3, RNF4) justifica aquele passo.

SCRUM-23-rf-5-editar-usuario

1 · Feature branch

Gatilho: o dev começa uma história do Jira
  1. 1.1

    Criar a branch pela issue do Jira

    Rastreio
    O que acontece

    O botão "Create branch" da issue gera o nome com a chave e o requisito: SCRUM-23-rf-5-….

    Por que existe

    A chave liga a branch à issue no painel Development. O rf-5 no nome já aponta para o requisito RF5 do README.

  2. 1.2

    Commits com a chave na frente

    Rastreio
    git commit -m "SCRUM-23 feat: editar usuário com validação"
    O que acontece

    Cada commit aparece na issue do Jira. No GitHub, o autolink transforma SCRUM-23 em link para a issue.

    Por que existe

    Hoje os commits dentro das branches saem sem a chave, por exemplo feat(user): implement…, e somem do rastreio.

  3. 1.3

    Branch de vida curta

    Fowler #4
    O que acontece

    Uma história por branch, aberta e mergeada em 1 ou 2 dias.

    Por que existe

    Fowler: integrar pelo menos uma vez por dia. Quanto mais tempo a branch fica separada, mais caro e arriscado fica o merge.

Rodar o Actions em todo push da feature branch ajuda, mas para o Fowler isso é "semi-integração": o código ainda não se juntou ao dos colegas. A integração de verdade acontece na etapa 2.

PR → develop

2 · Job ci no Pull Request

Gatilho: pull_request para develop, homolog e main
  1. 2.1

    Validar o título do PR

    RastreioCI
    título precisa casar com ^SCRUM-\d+
    O que acontece

    O PR fica vermelho se o título não começar com a chave do Jira.

    Por que existe

    Os PRs #3 e #4 entraram com o commit feat(tests): … e SCRUM-15 e SCRUM-16 perderam o vínculo com o código.

  2. 2.2

    Instalar dependências

    CIFowler #1 #2
    actions/setup-node (Node 20, cache npm) npm ci
    O que acontece

    Uma máquina limpa instala exatamente as versões do package-lock.json.

    Por que existe

    Prova que o projeto sobe só com o que está no repo. Acaba o "na minha máquina funciona".

  3. 2.3

    Checagem de tipos

    CIFowler #7
    npm run typecheck npm run typecheck:test
    O que acontece

    O TypeScript valida o código e os testes sem gerar arquivos.

    Por que existe

    É o passo mais barato e falha em segundos. Rodar o rápido primeiro mantém o build bem abaixo dos 10 minutos que o Fowler recomenda.

  4. 2.4

    Subir Postgres 16 e rodar as migrations

    CIFowler #9
    services: postgres:16-alpine npm run migration:run
    O que acontece

    O Actions sobe o mesmo Postgres do docker-compose.yml e aplica as migrations do TypeORM.

    Por que existe

    Os testes atuais usam repositórios em memória. Nada verifica SQL e migrations num banco real. Fowler: testar num clone de produção.

  5. 2.5

    Rodar os testes

    CIFowler #3RNF3
    npm test # vitest run: unit + HTTP com supertest
    O que acontece

    Roda os testes de casos de uso (UpdateUserUseCase.test.ts…) e de rota (updateUser.http.test.ts…).

    Por que existe

    Um build que se testa sozinho. É o RNF3: verificar automaticamente que tudo funciona antes de publicar.

  6. 2.6

    Compilar

    CIFowler #2
    npm run build # tsc → dist/
    O que acontece

    Gera o dist/ que o npm start executa.

    Por que existe

    Garante que o artefato que vai para produção compila, e não só os testes.

  7. 2.7

    Regra da branch develop

    Regra
    O que acontece
    • Só entra por PR, sem push direto nem force-push
    • O check ci precisa estar verde
    • A branch precisa estar atualizada com a develop
    • Squash usando o título do PR como mensagem
    Por que existe

    Um CI que dá para ignorar não protege nada. "Atualizada" faz o teste rodar no código já integrado. O squash com o título do PR garante a chave SCRUM no commit final.

develop

3 · Depois do merge na develop

Gatilho: push na develop
  1. 3.1

    CI roda de novo na mainline

    CIFowler #5
    O que acontece

    O mesmo job ci roda no commit que acabou de entrar na develop.

    Por que existe

    Dois PRs verdes podem quebrar quando entram juntos. Para o Fowler, a integração só termina quando o build da mainline passa.

  2. 3.2

    Develop vermelha: revert primeiro

    RegraFowler #6
    git revert <sha> # via PR "SCRUM-23 revert: …"
    O que acontece

    Quem quebrou desfaz o commit e investiga depois, numa nova branch.

    Por que existe

    "Ninguém tem tarefa mais prioritária do que consertar o build." Isso é combinado do time: o Actions não faz sozinho.

  3. 3.3

    Status visível para todos

    CIFowler #10
    O que acontece

    Badge do workflow no README e o check no PR. No Jira, a issue mostra o PR como merged.

    Por que existe

    Todo mundo precisa saber na hora se a mainline está saudável antes de puxar ou abrir um PR.

develop → homolog

4 · Homologação

Gatilho: PR develop → homolog, depois push na homolog
  1. 4.1

    CI no PR de promoção

    CI
    O que acontece

    O job ci roda sobre o conjunto de histórias que está sendo promovido.

    Por que existe

    Confere o pacote inteiro antes de ele sair da develop.

  2. 4.2

    Merge commit, nunca rebase

    RegraRastreio
    O que acontece

    A homolog recebe os mesmos commits da develop, com o mesmo SHA.

    Por que existe

    Hoje o rebase cria SHAs novos: SCRUM-23 é cdc4034, 96a3379 e 43b488c. Com o merge commit, um SHA vale nas três branches.

  3. 4.3

    Deploy em homologação

    CDFowler #9 #11RNF4
    build da imagem → migration:run → subir a API (destino a definir)
    O que acontece

    A versão da homolog é publicada automaticamente num ambiente igual ao de produção.

    Por que existe

    O time e o cliente validam as histórias num ambiente real. O deploy por script evita passo manual e erro humano.

  4. 4.4

    Smoke test na API publicada

    CD
    GET /api/stations → espera 200
    O que acontece

    Uma chamada simples confirma que a API subiu e fala com o banco.

    Por que existe

    Pega erro de configuração do ambiente (variável faltando, banco fora) logo após o deploy.

homolog → main

5 · Produção

Gatilho: PR homolog → main, depois push na main
  1. 5.1

    CI + aprovação de uma pessoa

    CIRegra
    O que acontece

    O PR só é liberado com o check verde e a aprovação de quem validou a homologação.

    Por que existe

    Fowler: com a mainline sempre pronta, liberar para produção vira uma decisão de negócio. Também evita outro caso como o PR #1, que entrou direto na main.

  2. 5.2

    Deploy em produção

    CDFowler #11RNF4
    O que acontece

    O mesmo script da homologação publica a versão da main.

    Por que existe

    RNF4: toda atualização é publicada automaticamente e o cliente sempre usa a versão mais recente.

  3. 5.3

    Tag e release com as chaves

    CDRastreio
    v0.2.0 - SCRUM-22 cadastrar usuário (RF5) - SCRUM-23 editar usuário (RF5)
    O que acontece

    A versão do package.json vira uma tag. As notas da release listam as chaves, que o autolink já transforma em links para o Jira.

    Por que existe

    Responde "em qual versão o SCRUM-23 foi para produção?". O Fowler indica tags como forma de marcar a maturidade do código.

O que o Actions não garante sozinho

  • Branches pequenas, de uma história só, mergeadas em 1 ou 2 dias.
  • Develop vermelha é prioridade do time inteiro: revert primeiro, investigar depois.
  • Toda branch, commit e PR começa com a chave SCRUM-NN.
  • Promoções entre develop, homolog e main sempre por merge commit.
